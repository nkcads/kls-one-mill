# KLSOneMill — vcpkg dependency pin
#
# vcpkg is used in CLASSIC mode here (there is no vcpkg.json manifest in this repo), which means
# the *vcpkg checkout commit* is the version lock: at a given commit, ports/<name>/vcpkg.json
# states exactly one version per port. Check out the commit below and you get the versions below.
#
#   repo    https://github.com/microsoft/vcpkg
#   commit  b81cab76a175645e047601da8f982ad86bff1cc3      (master, 2026-07-28)
#   triplet x64-windows-static                            (static libs + static CRT, matches /MT)
#
# Setup:
#   git clone https://github.com/microsoft/vcpkg <VCPKG_ROOT>
#   git -C <VCPKG_ROOT> checkout b81cab76a175645e047601da8f982ad86bff1cc3
#   <VCPKG_ROOT>\bootstrap-vcpkg.bat
#   ...then run the install lines below. They may also be combined into a single call, which
#   is faster (one dependency plan instead of fourteen):
#     vcpkg install --triplet x64-windows-static cpr libzippp pugixml spdlog clipper2 \
#                   nlohmann-json inja opencv flann libigl eigen3 boost-asio boost-geometry boost-system
#
# Set VCPKG_ROOT to that directory; CMakeLists.txt reads it and derives the toolchain file.
#
# IMPORTANT — also pass the triplet on the CMake command line:
#   cmake ... -DVCPKG_TARGET_TRIPLET=x64-windows-static
# CMakeLists.txt sets VCPKG_TARGET_TRIPLET only *after* including the vcpkg toolchain, so by
# then vcpkg has already resolved the default dynamic x64-windows prefix and find_package(cpr)
# fails with "Could not find a package configuration file provided by cpr". cmake-gui users do
# not notice because the triplet is already stored in their cache. CMakePresets.json sets it.
#

# ---------------------------------------------------------------------------------------------
# POST-INSTALL FIX — libigl ships a .cpp that includes a .c file the port does not install
# ---------------------------------------------------------------------------------------------
#
# Symptom, ~60 targets into a build of MeshLogic:
#
#   <VCPKG_ROOT>\installed\x64-windows-static\include\igl\ray_mesh_intersect.cpp(12):
#     fatal error C1083: Cannot open include file: 'raytri.c': No such file or directory
#
# Cause: libigl's own ray_mesh_intersect.cpp does `extern "C" { #include "raytri.c" }`, but the
# vcpkg libigl port (2.6.0#2) installs *.h and *.cpp and NOT the single .c file in the package.
# So a clean, successful `vcpkg install libigl` produces a tree that cannot compile
# igl::ray_mesh_intersect — which GeneralUtils/MeshUtils/Geometry/EigenGeometry.cpp uses.
#
# This is a THIRD-PARTY PACKAGING BUG, not an OneMill design problem: OneMill only calls a public
# libigl API. Nothing in this repository can fix it properly.
#
# Reinstalling libigl does NOT help — the port behaves identically every time. The fix is to place
# the missing file by hand:
#
#   copy raytri.c into <VCPKG_ROOT>\installed\x64-windows-static\include\igl\
#
# Obtain it from libigl's own source (it lives beside ray_mesh_intersect.cpp upstream) or from a
# machine that already has a working tree.
#
# HOW WE KNOW the port never installed it, rather than something having deleted it: on the
# reference dev box, ray_mesh_intersect.h and .cpp both carry libigl's upstream mtime of
# 2025-05-15 05:21:03, while raytri.c carries 2026-07-28 17:39:36 - the moment that toolchain was
# assembled. A file the port installed would share its siblings' timestamp.
#
# This step existed only as tribal knowledge until 2026-08-13, when a freshly provisioned CI agent
# failed on it at target 56/565. The build pipeline's pre-flight now asserts the file is present so
# a rebuilt agent or AMI cannot regress into that confusing C1083 again.
