# KLS OneMill — Release Notes
## Version 2.1.0

---

## UI

### Multi-Selection Holder Drawing
When multiple holes are selected and a holder is requested via the context menu, the holder geometry is now drawn for every selected hole simultaneously instead of only the focused one.

### Selection Block Marker
A new overlay widget indicates when an item's selection requires confirmation. The widget renders as a circle-with-handle icon positioned at the item's centre, always facing the camera. It is registered in the overlay renderer so it remains interactive even when other scene geometry overlaps it in the viewport. Clicking the marker once confirms the selection and activates the item; clicking elsewhere dismisses the marker without selecting.

### Layout Restructured
The main window layout has been reorganised for a cleaner workflow. Panel arrangement and splitter defaults have been revised to better reflect the typical usage sequence.

### Working Directory Confirmation
Before a new NC generation starts, the application now checks whether the selected working directory already contains files. If so, a dialog offers the choice to overwrite the existing output or generate a new timestamped directory, preventing accidental data loss from repeated runs.

---

## Configuration

### Milling Config Tab
A dedicated "Milling" tab has been added to the application configuration dialog. It groups module-specific options — currently post-processor output settings and all hole detection parameters — in one place, keeping the main workflow panels uncluttered.

---

## Rendering

### Render Prop Subtype Index
`RenderContext` now maintains a secondary index mapping each subtype to the set of registered prop IDs. `getRenderPropsBySubType` runs in O(k) time — proportional to the number of props of that type — instead of scanning all registered props. A new `getRenderPropBySubTypeAndUserDataId` method provides direct lookup by subtype and user data ID without allocating an intermediate vector. A `_lastBySubType` weak-pointer cache further reduces `getRenderPropBySubType` to O(1) for the common single-item case.

### GeomMarkCsysItem Shaft Visibility
Arrow shaft actors in the coordinate-system marker were missing ambient and diffuse lighting coefficients. Under scene lighting aligned with the shaft axis the diffuse contribution dropped to zero, causing the shafts to render black regardless of the assigned color. Ambient and diffuse coefficients are now set explicitly, matching the ring and sphere actors.

---

## Milling

### Hole & Csys Ref-Point Validation
Before generating an NC program, the application can now check that each hole's and coordinate-system's reference point sits on the correct side of the workpiece surface along its normal direction. The check raycasts along the normal (near vs. far side, configurable per operation) and compares the ref point against the surface crossings found, so it stays reliable even on imperfect geometry rather than requiring an exact match to a fixed tolerance. Holes or csys markers that fail are listed in the existing "Validation Warning" dialog before generation starts, with the option to continue anyway.

### Per-Operation Ref-Point Check Direction
Factory-standard drilling/milling entries gained a "hole validation direction" setting (Not Set / Near / Far), configurable per machining strategy. This determines whether — and from which side — a hole or csys is checked by the new ref-point validation; leaving it unset skips the check for that operation.

### Validation Success Confirmation
A new "Show info message when validation is successful" option (Milling config tab → Settings) shows a confirmation dialog before generation whenever the pre-generation validation finds no issues, giving the user a chance to cancel even when everything checks out. Off by default.

### Workpiece Validation on Machine Switch
Switching the milling machine now re-runs workpiece position validation after updating the fixture axis. Invalid holes and coordinate-system markers are immediately highlighted in the error color; previously they retained their previous color until the user moved the workpiece manually.

### Error Color on All Csys Parts
The `MillingItem.Error` color is now applied to all parts of a coordinate-system marker — ring, origin sphere, shaft actors, and cone actors — when a csys fails the angle check. Previously only the ring and sphere received the error color while the shaft actors remained in their default colors.

## Post-Processor

### Toolbreak Check After Drilling Operations
The post-processor now emits the `operation_toolbreak_check` code before a tool-change block when the preceding operation was a drilling operation, and at end-of-program when the last operation was a drilling operation. Non-drilling operations continue to emit the check in the operation epilogue as before.

---

## Performance

### Batch Rendering in SessionHandler
All color-assignment operations — `ReloadWorkpieceHoles`, `ReloadWorkpieceCurves`, `ReloadWorkpieceCsys`, `RefreshImplantHoles`, `ValidateWorkpiecePosition`, and `UpdateWorkpieceMatrix` — now defer VTK updates and issue a single `requestRender()` per logical operation instead of one render per item. On sessions with many holes this eliminates the per-item render storm that caused visible lag during workpiece loading and position validation.

### RefreshImplantHoles Merged
`RefreshImplantAdditionalGeometry` has been merged into `RefreshImplantHoles`. The workpiece matrix is computed once and applied to all three geometry subtypes (holes, orient holes, geometric IGES data) in a single pass. A `triggerRender` parameter lets callers suppress the intermediate render when a follow-up operation will request its own.

### HoleAngleChecker Inline Transforms
`CheckDrillingHoles` and `CheckCsysNormals` now transform direction vectors inline using a single homogeneous multiply (`positionMatrix * Vector4d(dir, 0)`), eliminating per-hole deep copies of geometry data. Result vectors are pre-reserved to avoid reallocations.

---

## System

### Parallel Behaviour Stabilised
Internal parallel processing has been stabilised. Edge cases that could cause inconsistent results or hangs during concurrent operations are resolved.

### Crash Reporting
The application now installs a Windows crash handler on startup. On any unhandled exception or access violation the log is flushed to disk and a minidump file (`KLSOneMill_crash.dmp`) is written to the log directory. The dump can be opened in Visual Studio with matching PDB files to obtain a full call stack with locals at the moment of the crash.
